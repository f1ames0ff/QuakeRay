# Stage-2 gate — 2026-10-10 (points A/B on the owner demos)

Method: one engine run per arm, each run `+exec` a config that carries the particle cvars, the arm
value and `rt_bench <demo> quit`. `perf\stage0\run_points_demo_ab.ps1` drives the four runs end to
end, asserts the game window into the foreground, sends one ESC after the window appears and caps
every run at 170 s. Build: the Debug binary of tree `ef41fdad` (resolve slot feed restored), one
binary for all four runs. Settings held by `config.cfg` and the run config: 3840x2160@165, FSR 3.1
Quality (`rt_upscale_fsr31=2`), `vid_vsync 2` (freesync), dtal master, `rt_particle_resolve_cache 1`,
`r_particles 2`, `r_particle_lighting 1`, `r_fteparticles 1`, `r_smoke 1`; the arm is
`r_particles_points {1,0}` (compact point transport against the legacy `QrVertex` transport for
classic triangles).

Demos (owner-recorded, `build\Debug\ad`):

  `2653D5878152894B2400514C282D7462094B1CBBCEEEA73FD10C5FEA5AD93C0F`;
- `ad_particle_idle` — 2,189,539 B, 54.1 s, SHA256
  `1A9642CA4D9FF36916B66BB2146FE34E9C9E01A3EC4A539BBBF5D5B28AB1C8C6`.

All values are `cpu.slot avg_ms` from the `rt_bench` blocks, read back through the engine MCP
(`read_benchmarks`); `frame` is the whole-frame bracket.

Paired deltas (on against off): heavy fps +1.6%, frame -1.6%, resolve -1.4%, upload -0.9%,
fte -1.4%; idle fps -0.2%, frame +0.3%, resolve 0%, upload -1.5%, fte -0.4%. The gate is <=5% fps /
<=10% slot regression: passed on both demos, and every delta sits at or below the ~1.6% two runs of
one arm differ by.

The classic path is empty on both demos (`particles_classic = 0`; the Stage-0 ablation saw
`points_off` as a no-op), so these arms prove the transport's passivity, not its win: the compact
point path is not exercised where classic sprites are absent, and it costs nothing there. The
transport's functional evidence with live classic sprites stays the stock `demo1` capture recorded
in the plan (~1090 sprites, no point-pipeline or validation warning); no owner demo with classic
sprites exists yet. The gate's upload-byte counter lives in the stats dumps (Stage-1 columns); with
the classic path empty on this content the transport moves the same bytes in both arms.

The same build restored the resolve slot the merge had left without a producer: `particles resolve`
reads again in every block (2.78-3.33 ms with the cache on), and the cache-off arm of the same
build reads 4.45 ms (`rt_particle_resolve_cache 0`), matching the corrected cache finding
(2.6 -> 4.3 ms).

`r_tasks 1` smoke (one `ad_particle_heavy` run, points on, the same config plus `r_tasks 1`):
2855 frames, 41.1 fps, `particles resolve` 3.35 ms, no crash or stall. Task-mode slot sums
accumulate worker wall times and are not comparable to the serial table above; the run exists to
show the feed and the merged render tasks coexist. Caveat, decision pending: the shared
point-cluster cache behind `RT_ResolvePointCluster` has no thread protection, and under `r_tasks 1`
the particle task and the brush/entity tasks call it concurrently (see the plan).

The runs were taken in an exclusive window (the MCP reported no game instance before and after).
Attempts whose window had lost the foreground measured 20.6-23.6 fps with slot values in the normal
range; the runner now calls `SetForegroundWindow`, which is why the four runs above come from one
clean session. A second clean session at `rt_particle_resolve_cache 0` (taken before the cache
archive was restored) measured heavy 36.1/36.3 and idle 38.0/37.8 fps, the same <=1.6% spread.
Absolute fps is not comparable with the 2026-10-08 baseline session (39.3-39.5 fps): the same demo
ran about 4-6% slower this session, so the acceptance reads the paired deltas, not the levels.
